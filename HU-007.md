# HU-007 — Registro de Reserva

**Épica**
Gestión de Reservas

**Sprint**
Sprint 2

**Prioridad**
Crítica

**Story Points**
13

**Dependencias**
HU-002 — Administración de Mesas
HU-006 — Consulta de Disponibilidad de Mesas

## Historia de Usuario

**Como** cliente del restaurante

**Quiero** registrar una reserva para una fecha y hora determinada

**Para** asegurar una mesa disponible antes de asistir al restaurante.

## Objetivo

Permitir que un cliente registre una reserva indicando sus datos de contacto, fecha, hora y cantidad de personas.

## Descripción Funcional

El cliente deberá proporcionar:

* Nombre.
* Teléfono.
* Correo electrónico.
* Fecha.
* Hora.
* Cantidad de personas.

Antes de registrar la reserva, el sistema deberá validar que exista una mesa disponible con capacidad suficiente.

La reserva deberá quedar asociada a una mesa y almacenarse inicialmente con estado:

* `PENDING`

Estados previstos para el proceso de reservas:

* `PENDING`
* `CONFIRMED`
* `CHECKED_IN`
* `CANCELLED`
* `NO_SHOW`
* `COMPLETED`

## Flujo

Ingresar Datos del Cliente
↓
Seleccionar Fecha y Hora
↓
Ingresar Número de Personas
↓
Consultar Disponibilidad
↓
Asignar Mesa Disponible
↓
Crear Reserva
↓
Guardar Reserva
↓
Mostrar Confirmación

## Reglas de Negocio

**RN-042**
No se podrá registrar una reserva para una fecha u hora pasada.

**RN-043**
La cantidad de personas deberá ser mayor que cero.

**RN-044**
La reserva solo podrá crearse si existe una mesa con capacidad suficiente.

**RN-045**
Una mesa no podrá asignarse a dos reservas que presenten conflicto de horario.

**RN-046**
Toda reserva nueva deberá iniciar con estado `PENDING`.

**RN-047**
La mesa asignada deberá encontrarse operativa al momento de registrar la reserva.

## Endpoint

```http
POST /api/v1/reservations
```

Ejemplo:

```json
{
  "customerName": "Carlos Pérez",
  "phone": "3001234567",
  "email": "carlos@example.com",
  "date": "2026-09-20",
  "time": "19:00",
  "guests": 4
}
```

## Validaciones

* Nombre obligatorio.
* Teléfono obligatorio.
* Correo electrónico válido.
* Fecha obligatoria y futura.
* Hora obligatoria.
* Cantidad de personas mayor que cero.
* Debe existir disponibilidad.

## Criterios de Aceptación

* El cliente puede registrar una reserva correctamente.
* La reserva queda asociada a una mesa disponible.
* La reserva inicia con estado `PENDING`.
* No se permiten reservas para fechas pasadas.
* No se permiten reservas sin disponibilidad.
* No se generan conflictos de horario sobre una misma mesa.
* La reserva queda almacenada correctamente en PostgreSQL.
