# Historia de Usuario

**Como** equipo de desarrollo

**Quiero** disponer de una arquitectura base del proyecto utilizando Node.js, TypeScript, NestJS, PostgreSQL, Prisma ORM y Docker

**Para** desarrollar las funcionalidades de reservas, pedidos y operación del restaurante bajo un entorno estandarizado, modular, mantenible, escalable y fácilmente desplegable.

---

# Objetivo

Construir la estructura inicial del backend de la plataforma de gestión del restaurante siguiendo buenas prácticas de arquitectura, modularidad, desacoplamiento, validación, seguridad y persistencia de datos.

La solución deberá establecer una base técnica que permita desarrollar progresivamente las funcionalidades relacionadas con:

* Clientes.
* Empleados.
* Mesas.
* Reservas.
* Menú.
* Categorías.
* Productos.
* Pedidos.
* Cocina.
* Pagos.
* Inventario.
* Notificaciones.
* Reportes.
* Auditoría.

La aplicación deberá estar preparada para soportar diferentes ambientes de ejecución:

* Development.
* Testing.
* Production.

El entorno deberá poder levantarse de manera reproducible mediante Docker Compose.

---

# Descripción Funcional

Se deberá crear la solución inicial del backend utilizando NestJS como framework principal.

La aplicación deberá implementar una arquitectura modular que permita agregar nuevas funcionalidades sin afectar innecesariamente los módulos existentes.

La plataforma estará orientada principalmente a dos procesos operativos del restaurante:

## Gestión de Reservas

El sistema deberá permitir posteriormente administrar todo el ciclo de una reserva:

```text
Consulta de disponibilidad
        ↓
Selección de fecha y hora
        ↓
Registro de reserva
        ↓
Asignación de mesa
        ↓
Confirmación
        ↓
Llegada del cliente
        ↓
Check-in
        ↓
Ocupación de mesa
        ↓
Finalización
```

## Gestión de Pedidos

El sistema deberá permitir administrar posteriormente todo el ciclo de atención de una mesa:

```text
Cliente / Mesa
      ↓
Apertura de pedido
      ↓
Agregar productos
      ↓
Enviar a cocina
      ↓
Preparación
      ↓
Pedido listo
      ↓
Entrega
      ↓
Solicitud de cuenta
      ↓
Pago
      ↓
Cierre del pedido
      ↓
Liberación de mesa
```

La arquitectura inicial deberá permitir incorporar estos procesos progresivamente mediante módulos independientes.

# Prisma Migrate

Todos los cambios estructurales realizados sobre la base de datos deberán administrarse mediante Prisma Migrate.

El sistema deberá conservar un historial versionado de las modificaciones realizadas al esquema.

El flujo esperado será:

```text
Modificar schema.prisma
        ↓
Crear migración
        ↓
Versionar migración
        ↓
Aplicar migración
        ↓
Actualizar PostgreSQL
        ↓
Generar Prisma Client
```

Durante desarrollo podrán crearse migraciones utilizando:

```bash
npx prisma migrate dev --name nombre_migracion
```

Para ambientes desplegados se utilizará:

```bash
npx prisma migrate deploy
```

No deberán realizarse modificaciones manuales sobre la estructura de la base de datos que no estén representadas mediante una migración versionada.

# Reglas de Negocio y Arquitectura

## RN-001

La aplicación deberá poder ejecutarse mediante Docker Compose.

## RN-002

Toda configuración dependiente del ambiente deberá obtenerse mediante variables de entorno.

## RN-003

La API deberá utilizar versionado y exponer sus recursos bajo el prefijo:

```http
/api/v1
```

## RN-004

Cada dominio funcional deberá encapsularse dentro de un módulo independiente de NestJS.

## RN-005

Los Controllers serán responsables de recibir solicitudes HTTP y delegar la lógica correspondiente.

No deberán contener directamente lógica compleja de negocio ni acceso directo a la base de datos.

## RN-006

La lógica de negocio deberá implementarse mediante Services o Providers especializados.

## RN-007

El acceso a PostgreSQL deberá realizarse mediante Prisma.

No deberá accederse directamente a la base de datos desde los Controllers.

## RN-008

Todo cambio estructural realizado sobre PostgreSQL deberá estar representado mediante una migración versionada de Prisma.

## RN-009

No deberán realizarse cambios manuales sobre el esquema de producción que no estén registrados mediante Prisma Migrate.

## RN-010

Los datos provenientes del cliente deberán validarse antes de ejecutar la lógica de negocio correspondiente.

## RN-011

La aplicación deberá utilizar `ValidationPipe` globalmente.

## RN-012

La documentación Swagger deberá mantenerse sincronizada con los endpoints implementados.

## RN-013

Los secretos, contraseñas y credenciales no deberán almacenarse directamente dentro del código fuente.

## RN-014

La infraestructura deberá permitir incorporar futuras integraciones mediante API REST.

## RN-015

La arquitectura deberá permitir incorporar progresivamente eventos, WebSockets, colas, procesos programados y microservicios cuando las necesidades del sistema lo requieran.
